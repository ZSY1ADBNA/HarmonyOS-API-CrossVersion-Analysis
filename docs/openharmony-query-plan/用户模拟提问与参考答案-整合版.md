日期：2026-10-10。
用途：先供余镕熙、张舒阳检查数据能否支撑真实开发需求，后用于 Agent 联调。所有问题均为团队模拟，不计作真实用户访谈。

## 使用与答案状态

- 平台固定 OpenHarmony。
- 以下参考答案是可用于组织数据的要点草案，不是已人工验收的标准答案。**静态核对**表示查到官方原文；**待补齐**表示部分事实仍缺同版本材料；**规则预期**表示助手应遵守的证据边界。全部尚待人工核查。
- 单版本要点先参考下列固定提交的 OpenHarmony 5.0.3 文档；它不表示团队已选定最终 SDK。跨版本示例使用 4.1 → 5.0.3，仅作为资料对，正式使用须核对双方声明和实际 SDK。
- 未编译示例、未运行设备、未核对数据库。本版不提供声称已运行的完整代码；U06 的完整示例仍待选定 SDK 后补齐。
- 已公开给数据组的题可用于开发。原步骤 02 的保留验收题划分不改；本版覆盖到这些能力后，最终独立验收应另出未用于调参的具体案例与表达。

每题按“当前数据能直接回答／需补结构数据／需检索官方文档／版本来源未定”记录实际结果。缺陷请附文件、节点、缺字段或错误关系与官方证据，避免只写“答得不好”。

## 20 道实际用户问题

### U01｜获取天气数据
**提问：** 我想在应用里从服务器获取天气数据，服务器提供的是 HTTP GET 接口。我应该使用哪些 API，基本流程是什么？

**参考要点〔静态核对〕：** 候选为 NetworkKit 的 http，导入 `{ http } from '@kit.NetworkKit'`；createHttp 创建 HttpRequest，调用 request，读取 HttpResponse，结束后 destroy。需要 INTERNET 权限。应说明请求对象的使用限制与错误处理，不只给函数名。依据 H：导入、createHttp、HttpRequest.request、destroy。数据检查：入口到对象、方法、结果类型和清理方法是否可关联。

### U02｜提交 JSON 表单
**提问：** 我需要把用户填写的表单以 JSON 格式提交给服务器。应该怎么发送 POST 请求，请求头和请求体分别怎么设置？

**参考要点〔静态核对〕：** request 的 HttpRequestOptions 中用 method 指定 POST、header 设置 Content-Type、extraData 放请求内容；JSON 序列化形式需与服务端约定对应。给出相关属性类型与同版本示例，不把任何对象都断言为已正确序列化。依据 H：HttpRequestOptions、RequestMethod、POST 示例。数据检查：配置类型、属性说明和枚举关系。

### U03｜请求超时
**提问：** 有时候网络很慢，我不希望请求一直等下去。能设置超时时间吗？连接超时和等待服务器返回数据的超时有什么区别？

**参考要点〔静态核对〕：** connectTimeout 控制建立连接的超时，readTimeout 控制读取超时，单位毫秒；H 对两者列出默认 60000。不能把这个默认值扩展到未经核对的版本，也不能将读取超时简单理解为所有异步工作的统一时限。依据 H：两个属性。数据检查：单位、语义、默认值及来源分别保存。

### U04｜async/await 与 callback
**提问：** 我的代码主要用 async/await。发送 HTTP 请求应该怎么写？如果官方示例用的是 callback，我应该怎样选择合适的调用方式？

**参考要点〔静态核对〕：** 选择返回 Promise<HttpResponse> 的 request(url, options?)，配合 await 与异常处理。callback 是另一组重载，不能把它的返回值当作 HttpResponse。依据 H：request 三组重载。数据检查：完整签名、异步形式、返回类型与重载能否分别保留。

### U05｜读取响应
**提问：** 请求成功后，我怎么取得响应状态码、响应头和返回内容？如果服务器返回的是 JSON，应该怎样处理？

**参考要点〔静态核对〕：** HttpResponse 的 responseCode、header、result 分别承载相关结果；结合 resultType/请求的预期数据类型处理内容。只有确认内容是字符串且符合 JSON 格式时才解析，并处理解析失败；请求完成不等于业务成功。依据 H：HttpResponse、HttpDataType。数据检查：返回对象展开、联合类型、状态与错误区分。

### U06｜最小完整示例
**提问：** 能给我一个最小的 HTTP 请求示例吗？希望包括导入、必要配置、发起请求、异常处理，以及结束后的资源清理，并附上官方依据。

**参考要点〔待补齐〕：** 应包含 U01 的入口和权限配置、Promise 或 callback 中一种明确形式、失败处理和可靠的 destroy 清理。H 有导入及调用示例；完整项目配置、目标 SDK 编译结果仍需补齐。不得只贴 request 一行就判为完成，也不得把改写代码称为已运行。数据检查：官方示例检索与结构数据能否一起支撑回答。

### U07｜语音备忘录
**提问：** 我想做一个语音备忘录功能，用户点击按钮开始录音，再点击结束并保存音频。需要哪些 API，应该按什么顺序调用？

**参考要点〔静态核对〕：** 可使用 media.createAVRecorder；注册状态/错误事件，准备录音配置及有效输出文件，prepare 后按状态机 start、stop，最后 release。文件输出与对象释放分别说明，不把 stop 返回值当作音频数据。依据 R：开发步骤、状态机和示例。数据检查：对象生命周期、方法与指南、输出配置的关联。

### U08｜录音权限
**提问：** 录音功能需要申请什么权限？在配置文件里声明后就能用，还是还需要用户授权？用户拒绝时应该怎样处理？

**参考要点〔部分静态核对，待补齐〕：** R 明确 MICROPHONE 及向用户申请授权；声明不代替授权。拒绝后不要继续假定录音可用，应向用户解释并停止相关操作。具体授权 API、配置片段、权限级别及再次请求规则须补同版本权限文档。数据检查：权限名称、授权方式和适用条件不能只留一个字符串。

### U09｜人声录音配置
**提问：** 我的录音主要用于保存人声，不需要很高的音质。采样率、声道和编码格式应该在哪里设置，选择时有哪些限制或建议？

**参考要点〔部分静态核对，待补齐〕：** AVRecorderConfig 的 profile 对应 audioSampleRate、audioChannels、audioCodec、audioBitrate、fileFormat 等配置。R 的示例值只是示例，不是默认值或所有设备的最佳组合；支持范围需补配置类型与编码能力资料后再推荐。数据检查：嵌套类型、枚举、约束和选型依据。

### U10｜下载完成通知
**提问：** 下载任务完成后，我想给用户发一条通知，显示标题和内容。应该使用哪些 API，还需要做什么准备？

**参考要点〔部分静态核对，待补齐〕：** 候选 notificationManager.publish(NotificationRequest)，核查通知使能、应用身份、通知内容类型及标题正文配置。N 提供 publish 与使能相关 API；标题正文的完整结构须补 NotificationRequest 关联类型资料。不能推荐已废弃的无参使能接口而不解释版本。数据检查：发布方法、配置类型、使能条件和废弃标记。

### U11｜更新和取消通知
**提问：** 我想在下载过程中更新同一条通知的进度，结束后改成“下载完成”，而不是不断产生新通知。如果用户取消下载，怎样撤掉对应通知？

**参考要点〔部分静态核对，待补齐〕：** N 说明相同 id 和 label 的发布会替换原通知，并提供 cancel。须同时维护通知身份；进度内容具体字段、支持的通知类型和设备展示效果仍待核对，不因支持替换就承诺任意进度样式都支持。数据检查：通知身份、更新规则、取消重载和配置类型。

### U12｜保存应用配置
**提问：** 我想把应用的配置保存到本地文件，下次启动再读取。应该使用哪些文件 API，文件适合放在哪里，需要额外权限吗？

**参考要点〔部分静态核对，待补齐〕：** CoreFileKit 的 fileIo 提供打开、读、写、关闭能力；优先核查应用上下文的 filesDir 等应用私有目录。必须区分私有目录和公共文件访问，不能笼统说所有文件操作均需或均无需额外权限。依据 F 的 API，目录与权限结论须补目标版本文件管理指南。数据检查：路径场景、访问边界、文件句柄生命周期。

### U13｜分段读取大文件
**提问：** 我需要读取一个比较大的本地文件，但不想一次把整个文件加载到内存。有没有分段读取的方式，应该怎样使用？

**参考要点〔部分静态核对，待补齐〕：** F 的 read/readSync 支持缓冲区及读取选项，readSync 返回实际读取字节数；使用受控大小缓冲区、正确推进位置、按实际读取数处理数据并关闭文件。具体选项的偏移语义和 EOF 处理要对所选重载核对后再写代码，不能混用其他文件对象的规则。数据检查：选项类型、返回数值语义、示例。

### U14｜网络状态及变化
**提问：** 发起下载前，我想判断设备有没有网络，以及当前是 Wi-Fi 还是其他连接。应该查询哪些 API？网络变化时能收到通知吗？

**参考要点〔部分静态核对，待补齐〕：** connection.hasDefaultNet 判断是否存在默认激活网络；getDefaultNet/getNetCapabilities 可用于进一步查询能力，相关方法需核对 GET_NETWORK_INFO 权限。默认网络存在不保证目标服务器可访问。变化监听须补 NetConnection 注册、事件和注销的同版本流程。依据 C。数据检查：能力类型、事件、权限及可达性边界。

### U15｜系统拍照界面与自建预览
**提问：** 我想让用户拍一张照片作为头像。如果希望使用系统提供的拍照界面，而不是自己实现相机预览，有没有适合的方式？两种方案在 API 使用和权限上有什么区别？

**参考要点〔部分静态核对，待补齐〕：** P 提供 CameraKit 的 cameraPicker.pick(context, mediaTypes, pickerProfile): Promise<PickerResult>，需要相应 UIAbility 上下文和相机能力。自建预览是另一条流程；双方权限差异、输出结果处理和适用设备须补资料后比较，不能将一方的限制直接套用另一方。数据检查：候选方案关系、能力条件、输入和结果类型。

### U16｜连接低功耗蓝牙设备
**提问：** 我的应用需要连接一个低功耗蓝牙设备并读取数据。从发现设备到连接、读取数据，大致需要哪些 API 和权限？设备或系统有什么前提条件？

**参考要点〔部分静态核对，待补齐〕：** BLE 发现设备后，可经 createGattClientDevice 创建设备客户端，连接、发现服务、读取特征，最后断开/关闭；B 提供相关 API。需要补齐扫描、蓝牙开关、权限、状态事件与 GATT 特征可读性条件；仅有设备 ID 不保证可成功读取。数据检查：跨对象流程、UUID/服务/特征类型、设备和权限条件。

### U17｜HTTP 升级检查
**提问：** 我们的应用准备从 OpenHarmony A 升级到 B，目前用到了 HTTP 请求功能。相关接口有哪些变化，哪些地方需要检查？请给出两个版本的依据。

**参考要点〔待双端声明核对〕：** 明确 A→B，按入口、全部重载、配置、结果类型、权限、能力和废弃标记比较，并列出双端证据。H 文档有 addressFamily 可选属性和 API 15 标记，HA 中本轮未找到该文字；这只是后续核查线索，不能据此认定其最早引入发行版或 A 中必然不存在。旧代码是否编译失败还需具体代码与 SDK。数据检查：快照身份、签名、关联类型和来源。

### U18｜新 API 在旧项目中是否可用
**提问：** 我在较新版本的官方文档里看到了一个适合的 API，但项目还使用旧版本。这个 API 在我的版本里能用吗？如果不能，有没有经过核实的替代实现方式？

**参考要点〔规则预期〕：** 补齐具体 API、项目发行版、API Level 和 SDK 范围，查旧版声明、导出及能力要求后判断。新文档 since 不能独自证明当前项目可用；替代流程需同版本证据，找不到时说明未知。数据检查：版本适用性、公开范围和替代证据，不能按名称相似自动替代。

### U19｜废弃与替代
**提问：** 我正在使用的 API 被标记为废弃了。官方建议改用什么？能直接替换，还是参数、返回值或使用流程也需要调整？

**参考要点〔静态核对示例，具体题待定〕：** 先定位 API。N 可作为实例：无参 requestEnableNotification() 从 API 12 废弃，推荐带 UIAbilityContext 的形式；因此迁移要准备上下文，不能声称完全直接替换。废弃不等于删除，替代关系不等于同一实体，兼容性须核对。数据检查：deprecated、替代目标、原因、版本和双方签名。

### U20｜围绕同一方案连续追问
**提问：** 先问“我想做录音功能，推荐哪些 API？”；再问“你刚才推荐的方案需要什么权限，录音结果是什么类型，有没有同版本官方示例？”

**参考要点〔规则预期＋R 静态核对〕：** 持续使用首轮确定的版本与 AVRecorder 方案，关联 MICROPHONE、输出配置和 R 的示例。区分 start/stop 的方法返回类型与保存音频的文件产物，不突然切换方案或混入另一平台文档。数据检查：候选身份、类型与文档关联；上下文保持由 Agent 联调验证。

## 给数据组的回填模板

每题复制填写：

```text
题号／核查人／日期：
发行版本／SDK来源及提交／API Level／应用身份／设备：
当前数据可支持的必答点：
不足类型：结构字段／类型关系／版本对应／官方文档检索／来源未定／无不足
实际 JSON 文件与节点（入库后另填节点键）：
官方声明位置与文档段落：
缺口及建议（不要把猜测写成事实）：
人工核查结论：未核查／有证据／有冲突／待补材料
代码状态：无代码／摘录／改写未编译／目标SDK编译／设备运行
```

优先回填 U01、U04、U06、U07、U10、U17。能从声明可靠提取的身份、重载、类型、可选性、版本标记应进入规范数据；调用顺序、完整示例、默认行为和比较建议可由官方文档检索补充，不要求所有答案都塞进 JSON。实际字段问题另见 [OpenHarmony 数据问题反馈](../review-2026-10-10/OpenHarmony数据问题反馈.md)。
