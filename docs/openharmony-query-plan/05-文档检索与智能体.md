# 05 文档检索与智能体

任务量：中；当前部署无法复用时可能升为高。建议 1—2 人，文档与智能体两线可并行。依赖：步骤 01 的来源和步骤 02 的问题；真实接入依赖步骤 04。

## 必要知识

RAG 是先检索证据再生成；智能体可根据缺口继续选择工具。Hello-Agents 用于补学工具调用、RAG 和评估，不重新设置学习阶段。LangChain 单智能体为起点。LangChain 智能体基于 LangGraph，后续“引入 LangGraph”是指直接编排受控流程。

## 文档线

按标题、API 小节及示例切分，避免把一个完整签名或示例切断；保留平台、版本、提交、路径、章节、链接与原文。不同版本不能混入同一无标签资料集合。

入库前查阅[官方文档入库审计与踩坑记录](../official-doc-ingestion-audit.md)，了解 52 个 Kit 常见排版差异（H1 废弃容器识别、无二级标题文档兜底、C-API 枚举拦截及 FTS5 性能陷阱）。后续各 Kit 入库由负责 Agent 按需编写或适配专用脚本，不假设单一脚本全量通用。

先做名称、关键词和条件检索，用题集检查中文功能问题是否能找到证据。若出现稳定的语义召回不足，再增加向量检索并比较效果；没有必要一开始配置所有检索技术。

## 智能体线

取得实际部署代码后复用已有功能；不要把旧仓库的实现结论直接当成线上结论。接入 API 搜索、详情、使用条件、文档检索及版本比较工具，限定只读和执行预算。

流程：确定平台与版本 → 找候选 → 查结构和相关类型 → 查条件与文档 → 判断证据是否充分 → 补查或回答。版本不明时先澄清；找不到时说明查过的范围和缺口。

跨版本问题先确认起始和目标版本，分别检索双方声明及文档，再调用版本比较工具。回答包含双方事实、明确变化、引用和待核实事项。区分声明变化、文档说明的行为变化与未验证兼容性；缺任一端证据时说明缺口。对官方替代项只给有依据的检查建议，未编译或运行不承诺可以直接替换。

答案至少含目标范围、候选与理由、完整调用信息、限制、出处和未确认事项。权限不足、接口不存在和设备不支持不能混为同一结论。

保存工具名、参数、命中证据、失败和耗时。引用必须能定位所支持的事实，不能仅附仓库首页。页面提供候选、详情、出处和答案，图谱作为辅助浏览。

页面允许选择单版本或起始/目标版本，比较结果分别展示两端签名、条件、变化及出处。步骤 03、04 新批次通过后，文档同步补齐并执行相关问题回归，不需要另设扩展步骤。

## 实验与验收

可先用人工核对的固定数据检查工具选择，但最终用真实工具测试。准备“查到 API 但没有默认值”“参数类型需继续展开”“权限证据不足”等补查场景。设置调用上限，达到上限返回已核实结论和缺口，避免无限循环。

- [ ] 答案基于工具返回证据，而非先回答后查询。
- [ ] 每个关键事实的引用支持该结论。
- [ ] 无匹配、工具失败、版本不明有明确处理。
- [ ] 静态示例不宣称编译或运行成功。
- [ ] 跨版本回答有双方证据，资料不全时不会编造变化或兼容性结论。

产出：文档索引、单智能体、页面接入和可追踪调用记录。交给步骤 06 评测。
