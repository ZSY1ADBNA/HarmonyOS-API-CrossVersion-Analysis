# 01 官方来源与版本样本

任务量：中。建议人数：1 人。依赖：无；可与用户问题收集并行。

## 目标和必要知识

为后续提取、文档检索和参考答案提供能追溯到明确版本的资料。发行版本、API Level、SDK 目录名称不是同一个概念。声明文件描述调用契约，不等于功能实现源码。

Kit 是能力集合；模块入口是导入来源；命名空间组织名称；直接所属对象表示方法或属性属于谁。不要将这几种关系压成一个含义不明确的字段。

## 来源

- 声明：https://github.com/openharmony/interface_sdk-js ，重点查看 `api` 和 `kits`。
- 文档：https://github.com/openharmony/docs ，重点查看 `zh-cn/application-dev` 中 API 参考和开发指南。
- 示例：https://github.com/openharmony/applications_app_samples 。

先通过这些入口找到目标版本分支和文件，再固定提交。不要用最新 master 内容替代历史发行版，不凭已有目录如 API5.0 直接认定版本。官方仓库中存在接口不意味着 Public SDK 或设备必然提供它。

## 技术步骤

1. 查发行说明和 SDK 信息，核实版本名称、API Level 与现有数据的关系。
2. 选择声明、文档和样本能匹配的两个发行版本；记录选择理由，先取同一领域的小样本作为对照。
3. 固定各资料提交，保存仓库、提交、相对路径和官方链接。
4. 建立两版本的 HTTP 主样本、音频和通知补充样本，记录相关类型和导出入口。优先包含可核实的新增、删除、签名或限制差异；暂时无法对应的对象单独记录。
5. 取得队友当前部署代码，记录提交或文件快照，列出可复用搜索、工具调用和页面能力。

每份来源记录至少包含：平台、发行版本、API Level、仓库、提交、路径、获取日期和适用性核查状态。无法核实的对应关系保留“待确认”。步骤 03、04 扩大到其他领域或版本时，在此清单补充来源，不重新设立扩展步骤。

## 样本选择与历史问题

HTTP 样本用于复核返回类型和方法是否漏提取；音频用于重载和条件化版本注释；通知用于可选属性和类型识别。增加接口、函数、方法、属性、枚举、类型别名、命名空间和嵌套成员样本。它们是测试结构，不必一次覆盖整个领域。

不要重新全量审计；从历史报告定位已知失败样本，确认现状后使用。若样本无法用普通 TypeScript 解析，应保留原文和诊断，后续决定解析适配，不能静默跳过。

## 产出和验收

- 来源与版本清单。
- 声明、参考文档、指南和示例组成的实验样本包。
- 当前部署与已有仓库的差异和复用记录。
- [ ] 每个样本可追溯到固定提交。
- [ ] 发行版本和 API Level 已核实，或明确列出无法核实项。
- [ ] 文档和示例适用版本已检查。
- [ ] 两版本同领域样本和比较双方的证据能够定位。
- [ ] 数据收集不包含密钥和数据库密码。

上述资料支持步骤 02、03 和 05。
