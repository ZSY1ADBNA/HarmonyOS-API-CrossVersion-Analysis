# 02 用户问题与参考答案

任务量：中。建议 1 人整理，后续由 1—2 人进行问答评测。依赖：问题收集无前置；答案依赖步骤 01 的版本资料。

## 收集方法

先记录真实任务，再考虑系统怎样检索。通过官方仓库 Issue、讨论区、开发者帖子搜索：`OpenHarmony HTTP 超时`、`OpenHarmony 录音 权限`、`具体API名 错误码`、`具体API名 callback Promise`，以及 `OpenHarmony 版本A 版本B API变化`、`具体API名 废弃 替代`、`OpenHarmony 升级 编译错误`。可用站点限定搜索，例如 `site:github.com/openharmony OpenHarmony HTTP`，并检查仓库指向的其他官方托管渠道。A、B 在搜索时替换为已确定的版本名称。

Issue 和帖子不自动属于 OpenHarmony：逐条辨别平台、版本、设备、代码和具体诉求。无版本信息可作为需求线索，但补齐环境后才能成为参考答案题。保存链接和简短概括，不大段复制帖子。参考入口：https://github.com/openharmony/docs/issues 。

第二条路径是阅读官方指南和示例，把任务拆成“入口是什么、参数怎样填、先后顺序、权限、失败处理、释放资源”等问题。官方示例入口：https://github.com/openharmony/applications_app_samples 。

标记题目来源：真实提问、官方任务改写、团队模拟。模型生成的问题也属于模拟，不能计为真实访谈。

## 参考答案核查

声明确认签名、重载、类型和可选性；API 参考确认含义、默认行为、错误码与限制；指南和示例确认调用顺序。帖子回复作为线索，不直接作为正确答案。官方材料冲突时记录冲突，核对版本，暂不强行定论。

代码只能标为“示例摘录”“根据证据改写但未编译”“已在目标 SDK 编译”或“已在设备运行”；不要把阅读示例称为运行验证。

每题记录：编号、来源类别和链接、用户问题、平台/版本/API Level/应用身份/设备信息、预期候选、必答要点、官方证据位置、不能推断的内容、开发或验收分组、人工核查状态。

跨版本题额外记录起始版本、目标版本、对应 API、双方证据、已确认的声明差异、文档说明的行为变化和未验证兼容性。新增/删除需核对声明及导出范围；单次搜索无结果不能证明接口删除。迁移帖给出线索后，再查两个版本的声明、发行说明和迁移指南。

## 初始 20 道模拟题

以下全部是候选题，不是已完成的 API 参考答案。目标版本和具体证据须由步骤 01、02 填入。01—14 用于开发，15—20 暂留作验收；验收题应补充新表达并在最终评测前避免用于调参。

1. 我想发送 HTTP GET 请求，不知道 API 名称，应该从哪里开始？核对入口与相关对象。
2. 请求头和连接、读取超时分别在哪里设置？核对配置属性，不混淆不同超时含义。
3. 请求配置哪些字段必填、哪些可选？可选不等于存在默认值。
4. 这个请求方法在目标版本有哪些重载？分别列完整签名。
5. 我使用 async/await，应该选哪种形式？核对 Promise 重载和适用条件。
6. 返回结果的类型有哪些属性？展开返回类型，不能只显示类型名。
7. 完成请求后怎样释放资源？核对官方流程及限制。
8. 普通应用发送请求需要哪些权限？区分声明、授权方式和身份条件。
9. HTTP 请求报某个错误码是什么意思？提供具体接口与错误码后再核查。
10. 有没有同版本官方最小示例和导入方式？标明示例适用性。
11. 我想开始、停止录音，需要哪些相关对象和方法？调用顺序必须有指南依据。
12. 录音需要声明权限还是还需要用户授权？核对目标版本权限规则。
13. 录音配置里可选字段不填会怎样？默认行为必须有明确证据。
14. 通知对象的配置类型和枚举有哪些？核对类型与属性，而不是只查函数。
15. 我只说“鸿蒙上录音”，你能直接推荐吗？应先澄清平台和目标版本。
16. 我给出一个完全不存在的 API 名，系统返回什么？必须无匹配，不能随机展示。
17. 仓库里存在的接口为什么 Public SDK 找不到？核对系统标记及 SDK 范围，不直接断定原因。
18. 我的设备没有相关硬件，接口一定能用吗？说明能力要求和待检查条件，不保证运行。
19. 换一种表达询问请求超时，再追问官方依据，答案是否一致？检查事实与引用。
20. 如果目标版本的默认值文档没有找到，可以告诉我通常是多少吗？应说明证据缺失，不能猜默认值。

## 跨版本模拟题（纳入当前题集）

21. 从版本 A 升到 B，这个方法的参数、返回类型和重载有什么变化？分别给出两版本签名与出处。
22. 版本 A 的 callback 形式在 B 中还存在吗？核对全部重载，不以一次检索无结果断言删除。
23. 这个配置属性在哪个版本新增或变为可选？只报告已核实版本对中的变化，不能据两个快照断定最早历史版本。
24. 这个 API 在 B 中废弃了吗？官方推荐替代项能否直接替换？区分推荐对应与兼容性。
25. 两版本的权限、系统能力或公开范围变了吗？引用双方条件，不能由同名推断一致。
26. 为什么旧代码升级后可能编译失败？根据声明差异列检查项，未编译不确认实际根因。
27. 我把 A、B 顺序反过来问，新增和删除的方向能正确反转吗？比较结果必须明确方向。
28. 如果只有 A 的资料，能告诉我 B 改了什么吗？说明缺少另一端证据，不生成差异结论。

题集增至 28 道候选：01—14 与 21—26 用于开发，15—20 与 27—28 暂留作验收。全部仍待填入真实版本和核对答案，不能当成已经验证的差异。

## 后续候选

多个 API 的场景比较、开发板之间差异和旧代码自动定位。跨版本签名、限制和废弃差异已纳入当前步骤；设备现场排障和自动迁移正确性仍不作为承诺。

- [ ] 开发题与验收题分开。
- [ ] 包含无结果、版本不明、限制和追问。
- [ ] 跨版本题的差异方向正确，关键结论有双方证据。
