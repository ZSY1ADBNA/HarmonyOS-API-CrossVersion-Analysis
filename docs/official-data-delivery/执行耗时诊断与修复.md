# 执行耗时诊断与修复

日期：2026-10-11。范围：余镕熙官方文档与示例采集这次执行及后续续跑。结论：连接故障、首次大规模传输与实现过程共同造成长耗时；执行方式也有可避免的重复。已修复续跑、重试和错误分类，外部连接稳定性尚不能保证。

## 实际耗时与证据边界

本次会话首个已完成执行段为北京时间21:37:32.801至23:05:28.642，共87分55.841秒。123次父工具调用的调用至返回时间合计1166.84秒（19分26.84秒）；余下68分29秒包含后台下载/扫描继续运行、模型处理、整理与调度，不能视为纯模型耗时或纯空闲等待。异步工具返回不代表后台工作已结束，不能直接把父调用时间当作下载时间。

原始记录在本机会话日志；只分析首个已完成段，排除本次诊断。脱敏后的逐调用时间、标签和输出长度在忽略目录data/delivery/execution-trace-summary.json。七次工具输出截断是实际记录，导致补读。日志中的SSL/timeout关键词还可能来自代码和历史描述，因此不把关键词命中次数当作故障次数。没有操作系统CPU/磁盘采样，不能精确归因每一分钟，更不能宣称模型服务变慢。

十份归档共约8.75GiB，含210314文件；这是首次传输与解压核验的真实规模，不能拿后续热缓存测试推算首次下载耗时。固定提交、文件指纹、许可和LFS核验必须保留。

## 确认的原因与处理

1. **网络路线和传输策略反复切换。** 沙箱127.0.0.1代理不可达，直接连接也有失败；大ZIP和Git整包遇TLS/early EOF。此前曾轮流尝试curl、urllib、整包Git，方案建立过晚。此前已经改为固定提交浅目录与分批对象，并禁用隐式全历史下载。现在文档/示例默认auto选择git-batches，保留缓存，不再默认走大ZIP路线。外部TLS、代理和服务桥接没有被本次代码修复。
2. **重试预算叠加。** 原curl内部重试3次，Python外层尝试3次，curl进程外部等待上限5000秒；单来源最坏可消耗数小时，实际这次没有证据表明达到该上限。现只保留外层2次，curl无内部重试、连接10秒、传输180秒、低速30秒终止，子进程200秒兜底；urllib也增加180秒总预算检查，单次阻塞读仍可能多出最多约30秒。Git网络请求设置180秒上限。失败明确记录，不用更长等待掩盖故障。
3. **网络错误也拆分对象批次。** 原实现捕获所有Git错误后递归二分；连接故障会转成更多同样失败的小请求。现TLS、EOF、连接失败直接终止该来源，只有not our ref/unadvertised object等对象专属拒绝才拆分；已取得对象保留，后续仅补缺失对象。
4. **重复采集与重复解析。** 原重跑即使status=collected也重新Git检查、解压核验和文本扫描。现完整核验后保存凭证，以固定来源及归档/目录/账本SHA256确认可复用；扫描还核对所有输出指纹。任一变化即回到完整核验；--reverify可显式强制重做。旧数据没有凭证仍先完整核验，不能凭状态或文件存在跳过验证。每个来源独立保存结果，减少总清单写入失败后人工重验。
5. **实现错误与发布整理消耗。** 此前实际遇到autocrlf字节变更、Windows GBK读取、LFS指针与原件误判、总清单临时文件占用，均已修正。这些属于我应更早检查的前置条件。大报告直接打印导致截断和补读、为回填自身提交号追加发布也增加了操作；后续输出摘要并直接传递文件内容，按已有规范用Git历史定位自身提交，不为记录SHA反复补提交。

## 修复验证

16项回归实际通过，包含网络错误不拆批、对象专属拒绝才拆批、下载只有一层两次限时尝试、urllib按read1收到数据即检查预算而不等待填满大缓冲、续跑不启动Git、归档/账本/提交改变拒绝复用、扫描输出被修改后重新生成、总清单未落盘时按固定身份恢复分来源结果，以及此前LFS、文件指纹、自动换行、锁占用和来源身份测试。Python编译检查通过。

真实OpenHarmony-4.1示例：14949文件，归档407332019字节。使用PR #10原采集器进行完整核验，再用新凭证续跑；采集6.984秒→0.571秒（12.23倍）。扫描完整执行4.763秒→指纹核对后复用0.635秒（7.50倍）。指纹、文件统计、扫描失败项一致，9个已有解码失败仍保留，未把未完成状态改为通过。具体环境与结果见[performance-benchmark.json](performance-benchmark.json)。

这是同机、已有归档、热缓存、单来源测试，没有网络下载；不是整个88分钟任务的提速倍数，也没有完成干净环境全量重建。其余九来源尚未建立新凭证，首次续跑仍会完整核验一次；后续才可复用。

## 后续执行约束

- 开始下载前先核对已有固定锁和缓存；只做一次轻量连接检查，已确认不可达的执行环境不重复碰同一路线。
- 用小样本确认编码、Git原字节、LFS和对象完整性后再批量运行；继续已有工作时跳过有有效凭证的来源。
- 独立任务并行，依赖操作顺序执行；后台任务有进展时再读取摘要，避免密集无变化轮询。报告写文件，聊天只输出必要统计。
- 采集和扫描记录每来源elapsed_seconds及复用状态；这只能定位来源总耗时，若仍慢，再增加阶段和系统采样，不猜测模型/CPU瓶颈。
- 本次未改模型、账号、系统代理或全局Git设置；未改共享RAG/Neo4j和网站。SDK/语义/编译与成员验收待办仍按原计划推进。
