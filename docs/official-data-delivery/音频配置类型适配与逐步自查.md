# 音频配置类型适配与逐步自查

2026-10-12，本批扩展五类音频配置类型：AudioStreamInfo、AudioRendererInfo、AudioCapturerInfo、AudioRendererOptions、AudioCapturerOptions。读取五个正式发行的已锁定官方原文，旧布局为 js-apis-audio.md，新布局为 arkts-apis-audio-i.md。原文 SHA256 与已有文件清单逐一核对。

## 步骤一：核对版式与字段含义

发现旧布局采用“必填”，新布局采用“可选”，不能同向转换。新适配器把两者统一为 optional，同时保留原列名和原值。旧版没有“只读”列时存 null，不推断为可写。字段的版本、系统能力与废弃标签单独提取；接口元信息另存 parent_metadata，不将接口版本自动当作字段版本。

## 步骤二：实现后检查及修复

单独的 extract_audio_config.py 仅处理上述五类，不推广到全部 Kit。过滤围栏示例、方法参数和其他类型；每条属性关联对应配置接口，并保留类型、描述、原表格、原文行号和来源指纹。

复查增加了同一类型重复字段拒绝通过，以及数据输出路径边界检查。未知必填/可选/只读值、冲突列、列数错误、原文行缺失或错误发行集合均不能发布新批次。以原始非围栏字段行独立核对字段名称与行号覆盖，不能只验证程序输出自身。

8 项新增回归覆盖：旧/新列转换、字段和接口元信息隔离、示例及参数排除、同名字段不同归属、错误表格拒收、重复字段拒收、真实管线失败保留原有批次及中文命令行输出。完整 53 项测试通过。

真实查询检查发现 Windows 默认输出编码会让中文字段在工具结果中乱码；查询出口已显式使用 UTF-8，并通过默认编码为 ASCII 的子进程回归验证中文表头与说明能完整返回。原始文档和数据库文字没有被改写。

## 步骤三：真实五发行及独立检索验证

实际结果为 5 份输入、25 个配置类型候选、82 个字段候选；每个版本五类均有且仅有一个配置区段，字段行完整覆盖、原文范围一致、零表格警告。19 项批次检查通过，包括重复入库不增量、索引完整性、所有属性归属接口、按发行和类型查询、未知发行空结果与实际拒绝 DELETE。

实际查询分别核对两类 Options.streamInfo：必填状态一致，Renderer 与 Capturer 的系统能力分别保留；channelLayout 的字段版本为 11+，接口版本另存为 8+。6.1 的 volumeMode 为可选、19+，不出现在本次 4.1 配置页候选中；该空结果不是 SDK 不存在的证明。6.1 的 playbackCaptureConfig 废弃标签保留，缺少格式化起始版本时保留 null，同时完整保存说明正文。

成功批次在忽略目录 data/delivery/structured/yu-audio-config 中，通过 current.json 原子指向成对产物；共享库与先前语义批次未替换。默认查询仍指向先前语义试点；本批查询需明确选择批次：

```powershell
python tools/extract_audio_config.py
python tools/query_document_candidates.py --batch-root data/delivery/structured/yu-audio-config --release OpenHarmony-6.1-Release --owner AudioRendererOptions --name streamInfo --kind property
python -m unittest discover -s tools -p 'test_*.py'
```

--batch-root 会校验成对产物指纹；与 --database 互斥。检索仍为只读并限制返回条数。
